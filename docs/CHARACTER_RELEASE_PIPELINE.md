# 五星角色发布流程

本流程用于为《虚空裂变》持续加入完整的五星角色内容包。每次发布把角色机制、成长与推荐、专属祝福、角色剧情、遗物、搜打撤内容、美术、声音、旧存档兼容和更新包作为同一交付单元。设计定案后依次完成数据接入、资源制作、数值核对、受影响功能验收和发布核验；各阶段保留可追溯的结果。

新成体系的五星角色采用固定模板：每名角色 6 条可用专属祝福，分成 3 条体系共享与 3 条角色私有；两组各含白、蓝、金一条。体系搭档采用相同的共享标识和相同池规模。尚未形成配合体系的旧角色保持原池，待其配合机制确定后另行设计。本期火体系的卡尔迪与瑟琳各 6 条，艾拉原有 5 条及其内容、权重和条件保持原样。章节规模与搜打撤扩充量按各次立项单确认。

## 交付范围与完成定义

| 交付领域 | 每次发布应形成的成果 | 完成证据 |
| --- | --- | --- |
| 角色 | 名称、身份、元素、定位、基础与成长属性、技能、被动、命座、立绘与表情 | 数据表、战斗接入、角色界面 |
| 队伍与遗物 | 独立和组队目标、最优搭配比较、新套装、推荐目标与说明 | 同投入比较、推荐器输出 |
| 祝福 | 等量个人池、等量共享池、稳定标识并集去重 | 池结构断言、候选权重记录、旧档样本 |
| 剧情与获取 | 章节、试用、对白、敌人与首领、奖励、限定池与保底 | 原章节语言基准、叙事通读记录、首通与重放记录、领取与保底迁移记录 |
| 搜打撤 | 新环境主题、三张地图、独立容器、战利品、局内音乐 | 地图顺序、固定掉落、经济与存档记录 |
| 美术与声音 | 生产资源、图集、来源与授权清单、尺寸与播放预算 | 游戏内截图、循环试听、资源核对 |
| 版本交付 | 版本号、更新说明、验证清单、构建产物与签名 | 同一代码版本对应的验收与构建结果 |

## 第一阶段 固定角色与内容合同

立项首先确定角色的独立用途、与现有角色的关系和玩家可理解的核心玩法。把核心玩法写成简明技能文案，并同步记录引擎需要的触发者、目标、时点、持续时间、资源消耗和叠加方式。角色身份、技能关系与故事动机互相支持；队伍搭配通过技能机制实现，剧情体验面向所有达到解锁条件的玩家。

数值目标必须写出比较对象、投入预算、队伍第三人、遗物、命座、开场能量、敌人数、敌人防御与状态、战斗长度和祝福条件。单体面板强度与全队贡献分别计量。先固定目标和比较条件，再选择满足目标的技能与属性；每次修改都更新同一份定案，保存仍然有效的参数与结论。

角色内容包同时确定章节战斗与幕间数量、首领奖励、试用奖励、限定池规则、新遗物的获取路径，以及搜打撤新增环境主题、地图、容器和物品数量。确认后的标识与资源路径形成内容合同，程序、美术、音乐与文档共用这一合同。每次新增战斗场景或敌人，统一接入主线、深渊和搜打撤三种模式，作为默认完整交付范围；按各模式相同层级、相同遭遇类型的预算校准生命、攻击、防御、速度和整体编队，分别核对技能、附属目标与阶段机制。深渊采用独立 `abyssBaseStats` 按同类型归一后再应用既有层数曲线，章节基础值服务主线本身；已签发遭遇的敌人、场景和随机状态继续保留。

接入三种模式不等于共用一个动态候选池。每名新敌人必须明确列出各模式的候选入口、基础属性字段、成长曲线、编队和附属单位；旧主题的准入规则也应显式隔离，不能因深渊扩池而自动抽到主线规格的新首领。动手前回读[赫铎跨玩法数值案例](CROSS_MODE_ENEMY_BALANCE.md)：其中保留旧池泄漏、单体护卫预算转为群攻的实际原因与历史算式，并记录后续玩家 DOT 防护、群攻间隔和恢复动作要求。主线章节成长单独保留，不能用跨模式统一削弱代替定位预算错误。

### 剧情语言基准与写作参考

动笔前先回读[第三章改写案例](NARRATIVE_WRITING_REFERENCE.md)：旧驿站如何从凭空命令改成雪后救人，借火如何通过包扎、发抖与控制火焰建立关心，赫铎的心事如何从铜墙记录、呼唤和推测逐步显现。案例保留改写前后的完整短场景，说明具体缺口与处理办法；不要把下面的原则当成替代阅读原文的口号。

后续每次新增角色剧情，先通读 `godot/data/catalog.json` 中 `DialogueData` 的原第一章、第二章（`ch1_*`、`ch2_*`），以炎龙线的卡尔迪和艾拉登场章节为语言基准。保留这两章原文作为参考，不能为了适应新稿而反向压缩旧文。按旁白、旅行者、卡尔迪、艾拉分别摘取代表性段落，记录实际用词、词语的汉字数量、句子字数、分句节奏与人物口吻；句子字数以汉字计数并注明标点不计。新稿与对应角色、对应叙事位置的样本比较，避免凭印象另定一种短句风格，也不把样本长度变成每句必须凑齐的配额。

逐场写作先补全因果：人物从哪里来、为什么到这里、眼前看到了什么、在关心谁或担心什么、为什么决定行动，以及这次行动如何引出下一场。旁白通过人物的动作、观察与环境变化逐步呈现信息，让读者先看清具体处境，再理解人物判断。战前交代行动动机，战后回应行动结果与人物感受，转场说明继续前往下一处的理由；线索和情绪都应有前后承接。

对白应易懂、舒展顺畅，有情绪和具体关心。人物回应同伴的疲惫、伤势、害怕或愿望时，要结合眼前发生的事，不只泛泛表达责任。卡尔迪的爽直、热情和关切，艾拉的温柔、感谢与坚定，均从原两章的具体语句和语境延续；新角色则通过自身经历、观察和选择形成口吻，不能让全队都说同一种冷漠的战术口令。避免用连续格言、抽象比喻或口号代替事件推进和人物交流。

叙事中的动作写成完整自然的动词短语，明确必要的对象和意思，禁止“别硬接”“你护灯”“先灭侧灯，再开门”这类单字动词式省略。对照本次定稿的“及时躲避”“照看好收回来的铜灯”“先熄灭侧炉灯，再一起对付监工”，以及原第一章的“击退”“掩护”“并肩作战”，同时检查词语的汉字数量、搭配、句式与句子字数。这一语言要求不能被“动机清楚、有温情”代替，也不能只靠平均句长判定通过。实际修改要重读动作语境，不机械逐字替换；“护”在“掩护”中、“接”在“接过提灯”中并不是省略式单字指令。功能界面的按钮、提示和数值说明继续保持简洁，剧情旁白与对白则按叙事需要展开，不能套用界面文案的压缩方式。

人物的来由、所见、关心、行动和前后承接，是发现阅读缺口时回看的问题，不是每场必须按顺序填满的模板。救人后可以留出休息和玩笑，遇敌时可以急切，调查时可以慢慢发现；节奏随场景变化。本期第三章八关战前、战后共 16 段的改写经验保存在上述案例中，原前两章保持不变。后续新角色剧情先回读原章节和案例，再写作、通读；句长与词长比较用于发现突兀的压缩，不用于机械配额。

## 第二阶段 数据与系统接入

| 接入位置 | 应核对的内容 |
| --- | --- |
| `godot/data/catalog.json` | 角色、技能、命座、状态、祝福、敌人、章节、遗物、卡池及其引用关系 |
| `godot/data/extraction.json` | 环境主题、地图与容器池、容器类别、物品尺寸、稀有度、售价和经济设置 |
| `godot/scripts/battle_model.gd` | 动作顺序、技能触发、伤害类别、来源归属、持续状态和首领阶段；协同 `abyss_balance.gd` 校准模式预算 |
| `godot/scripts/game_model.gd` | 获取与成长、存档迁移、保底、奖励结算、祝福候选与推荐入口 |
| `godot/scripts/relic_sets.gd` 与 `relic_optimizer.gd` | 套装数值、穿戴者效果、实际评价目标与搭配结果 |
| `godot/scripts/extraction_model.gd` | 新局配置、幕数、地图与内容固定、探索奖励、寄送和撤离 |
| `godot/scripts/main.gd` 与 `scripts/ui/` | 角色详情、试用、章节导航、状态说明、立绘、容器、图标、动画和声音 |
| `godot/data/version.json` 与构建配置 | 版本名、版本码、包标识、正式更新源及签名一致性 |

所有新增内容使用稳定标识；改名保留原标识，旧字段采用明确的兼容映射。角色需要接入图鉴、抽卡结果、队伍编成、升级觉醒、技能与命座、遗物装备、定向获取和搭配推荐。描述与实际效果共享参数或经过一致性核对。推荐器按角色定位声明评价目标，支援角色展示全队增益依据，输出仍绑定实际库存和既有装备规则。

每个资源引用都应能解析到交付资源。结构检查覆盖唯一标识、引用闭合、有效稀有度、尺寸范围、资源存在和字段默认值。对引擎中硬编码的角色清单、最终幕判断、元素筛选、图标映射和章节数量逐项检索；使新增内容沿既有入口自然出现。

## 第三阶段 旧存档与奖励连续性

迁移以玩家已有状态为起点，仅补充新版本所需字段。角色培养、遗物、物品位置、货币、关卡进度、已领取奖励、抽卡累计次数、保底计数与大保底状态持续保留。新增里程碑奖励采用稳定领取标识，重复进入、保存与重启均只发放一次。

新装备接入须按实例 UID 检查穿戴身份跨出发、撤离和读档保持，不能撤离时混入普通仓库后被一键出售；本期以独立三槽 `extraction.tactical` 与 `run.equipped` 往返保存，并由模型层 `protected_item()` 保护出售入口，而不只隐藏界面按钮。同 `itemId` 或同属负 `damageTakenMult` 减伤效果族的装备互斥，替换须保留旧物 UID 与财产。旧重复装备在安全状态退回背包或待领取区；背包／仓库及待领取区都满时保留原状态待处理，不销毁物品、不重置存档，也不在进行中的战斗里改穿戴效果。无法追溯穿戴身份的旧仓库物品不得猜测后自动装备。

进行中的搜打撤局携带自己的总幕数和已确定主题顺序。每局固定三幕，新局在开局时打乱全部可用主题并取前三种，形成无放回选取的固定顺序；当前四种主题选三种，未来主题池扩充后沿用相同规则。旧局保持原已选主题顺序。已生成地图、容器内容、已搜索状态、背包摆放与战前随机状态保持原值。战斗中恢复继续采用同一遭遇固定战前状态。已选祝福按原标识解析；共享池改造后仍保留既有层数与效果。

敌人预算与候选修复只在新生成遭遇时应用，已有 `activeEncounter` 的敌人、倍率、种子和配置不在读取时重算。新场景将节点生成时已确定的 `node.background` 冻结到战斗 `config.background`；旧已签发配置缺字段时使用只读显示回退，不写回配置、不额外推进 RNG。验证应同时比较战斗配置与完整随机状态，不能只看屏幕上仍然是同一只怪。

容器保底必须检查最终实际装入并可领取的物品，不能只确认抽到了保底。本期首领箱曾因物品尺寸与贪心摆放顺序丢掉第四件：现在仅在首领箱摆放失败时用 `_packed_copy()` 完整重排，再按 UID 恢复抽取与揭示顺序，不额外消耗 RNG。后续扩充物品尺寸、容器或掉落权重时，应同时检查件数、保底品质、实例身份与实际装箱结果，不能让装箱过程悄悄削掉已抽中的奖励。

迁移样本覆盖新档、普通旧档、含新字段的重读、旧三幕进行中、战斗中、待领取奖励、保底临界、已选共享祝福和仓库溢出。迁移过程须可重复执行；第二次读写得到与第一次相同的游戏状态。

## 第四阶段 祝福池结构与抽取

每名新成体系的五星角色固定 6 条可用专属祝福，其中体系共享 3 条、私有 3 条，两组均各有白、蓝、金一条。同体系成员保持相同池规模与共享数量。未来加入同体系角色时沿用共享条目的稳定标识。尚未形成体系的旧角色保留既有祝福内容、数量、权重和条件；其体系化改造作为后续明确确认的内容处理。通用祝福池维持原有功能和容量。

同队可用专属池以条目标识求并集。一个共享条目在候选池中占一张票，按其稀有度和既有规则计算一次权重。共享条目始终以固定一票和固定权重参与抽取，角色聚焦权重更新仅处理其他符合原规则的条目。分类筛选建立在去重后的集合上。展示中的“可用数量”“已选数量”和实际抽取集合保持同一口径。

| 检查样本 | 预期 |
| --- | --- |
| 单名已成体系五星 | 6 条，白蓝金各 2 条 |
| 同体系双五星 | 共享 3 条计一次，合计 9 条 |
| 两名采用新模板的独立体系五星 | 以实际稳定标识并集计数；通常为 12 条 |
| 尚未成体系的旧五星 | 保留原池及抽取规则；艾拉本期维持 5 条 |
| 同一角色重复加入输入 | 候选条目与权重保持相同 |
| 已选共享祝福旧档 | 原标识、层数和效果持续有效 |
| 通用池与角色池合并 | 同标识只留一条；每条沿现有规则参与抽取 |
| 队伍顺序交换 | 候选集合和每条权重相同 |

数量、分组与候选票数采用确定性断言验证。已有祝福的层数规则继续生效；新增上限需单独进入已确认的设计合同。

## 第五阶段 战斗数值与动作顺序

每个技能记录完整时序：开始动作、扣能量或检查冷却、主段命中、技能附加状态、原生追击、技能完成效果、主动动作后效果、持续时间结算及轮到下一行动者。新增增益从实际施加时点开始生效；首轮触发与后续覆盖分别计算。阵型只调整速度排序后相邻的己方行动段，敌方行动边界由速度决定。

持续伤害记录施加来源与需要快照的属性。伤害报告分别列直接伤害、追击、持续伤害、行动后引爆和额外触发。每类伤害明确暴击、防御、属性加成、燃烧加成、伤害加深、受伤修正、击中触发与能量回流的适用范围。相同加成放入既有加算区间后统一结算一次，独立区间之间按已确认公式计算。

能量模型覆盖普攻、战技、终结技、被动、受击和祝福的实际入口。计算模型使用实装的动作完成时点、能量上限、溢出处理和冷却规则。以微光 16 层为例，非终结技回能增幅为 16 × 15% = 240%；冰冻体系 15 次、每次 12 点对应 180 点回能。每次比较同时保存行动序列和各行动能量，便于核对高频终结技场景。

最优搭配比较分别覆盖零命与满命、基础培养与毕业投入、低祝福搜打撤和 100 条祝福的高构筑条件。对照角色使用自身实际最优遗物，而非强行统一套装。配队比较维持相同第三人和总投入，并声明替代输出位的机制及其对灼烧、冻结、行动顺序和团队加成的依赖。结论用适用区间表达，并附实际样本；设计期望计算与引擎实战结果分开归档。

新敌人不能只对齐生命和攻击总和。普通、精英、首领分别指定旧同类的明确基准（例如监工对黑暗骑士、赫铎对女巫），按双方完整编队比较辅助增益、护盾、群攻目标数与意图概率、主动攻击率、六行动输出、单人及全队峰值、冷却、阶段和完整循环，不能只用旧首领均值。玩家承受的燃烧、中毒等负面伤害继续经过有效防御、普通减伤与技能盾、装备盾吸收，玩家 DOT 打敌保留原有机制。调整节奏必须采用这条当前伤害链，不能防护已经修好后仍按旧穿盾压力大砍行动率：2.7.5 监工、赫铎每次攻击后强制无伤与额外观察过弱，已由 2.7.7 两目标远征配置 `aoeChance: 0.5`、`recoveryPolicy: "single"` 替代；普通怪、主线和旧敌人不随之回调。群攻跨技能禁止连续，之后可用较低全队压力的单体继续参与，普通攻击不机械停手；恢复窗口不等于频繁空过，单体仍须核对被选中玩家的峰值。低防御、高防御与有盾条件分开检查，注明假设的小规模公式不冒充实战。案例保留旧预算、玩家防护和过度削弱的演变，历史算式不得充当新规则结果，单个怪物的折算系数也不得推广为通用常数。

## 第六阶段 视觉与声音资源

立项单记录角色全身立绘、头像、表情、抽卡横幅、技能图标、祝福图标、遗物图标、章节背景、剧情插图、敌人、首领、可选中的首领附属部件、独立容器和战利品的数量与用途。共用风格要求和资源预算在开工前确认，资源清单记录目标分辨率、格式、透明通道、压缩体积、全量解码理论占用、实际场景显存预算、图集位置与使用场景。以本期模板为例，全身立绘 1024×1536、横屏场景 1672×941、敌人与容器 512×512、物品 256×256、技能与遗物图标 384×384；每次发布按目标设备重新确认规格与同时加载数量。

战斗中的角色与敌人以固定脚底锚点和等比缩放展示，头像单独裁切。容器与可交互物件使用独立透明层；场景背景承担空间与光照。不同品质使用可识别的颜色、品质框和图标组合，文字与触控目标保持清晰。图集分块预留足够透明边距与安全扩边，按实际过滤方式检查邻格串色；逐格核对完整边缘、透明背景、尺寸和命名。

每名新角色分别适配战斗全身、半身展示、头像与小头像，不能只确认资源存在或人物比例接近。瑟琳曾把全身图直接缩进半身卡，导致人物偏小；随后方形 `AtlasTexture` 裁切虽改善比例，却在宽幅背景内部留下衣袖和腰部的悬浮硬边，说明只核头部大小仍不够。半身展示现由 `character_bust.gd` 使用完整透明源图，`BUST_REGIONS` 仅作为缩放、居中和顶部留空的构图参考，不是切断人物的边界；手、灯、发丝和身体可越过参考区自然延伸，实际裁切只发生在画框边缘。验收时须与同屏旧角色对照头部尺寸、眼线、肩宽和上身占比，同时看清头顶、发丝、手、灯和衣摆边缘是否自然结束或由画框遮挡，不能在背景中间一刀切。逐一检查编队、抽卡单次揭示与结果卡、旅者档案和角色详情，不能只改通用卡片后就认为所有入口已覆盖。头像与小头像仍使用各自头像区域或独立资源，不能套用半身构图规则；半身调整也不得改坏战斗全身源图、等比缩放与脚底锚点。

角色展示还应统一验收推荐与背景：推荐由 `relic_set_recommendations()` 读取同一角色的 `relicObjective.recommendedSets`，图鉴、养成按钮与推荐弹窗的首项保持一致（瑟琳为 `ember_lantern`）；`_portrait_environment()` 按显式 `background_path`、角色 `portraitBackground` 有效资源、通用元素缺省背景的顺序取图，优先使用已配置的专属场景（瑟琳为 `unlit_town.png`），并保留独立 banner 显式背景参数的最高优先级。

音乐以原创或有明确使用授权的资源交付。每个新环境采用 60–90 秒可循环主题音乐及变奏，主线、深渊和搜打撤按场景功能绑定对应曲目，章节与首领可复用适用的同主题变奏；常规反馈提示音约 0.15–0.5 秒，大招前奏、尾音和抽取主题提示按演出需要可延长至约 1–1.5 秒，按类别分别记录。查看背包、角色详情、奖励等辅助界面沿用当前音乐，主场景切换才执行交叉淡入淡出。声音清单记录时长、采样率、声道、编码、循环接点、响度与峰值预算；同时验证静音、音量、暂停恢复和场景释放。

来源清单逐项登记文件路径、创作者或生成方式、授权依据、生成或取得日期、编辑过程和校验摘要。实际游戏内验收包括透明边缘、黑底污染、人物比例、脚底位置、品质识别、图集串色、音乐接点和提示音清晰度。

## 第七阶段 受影响功能验收

代码与资源整合完成后，集中进行一次必要验收，受影响游戏功能检查与真实界面检查合计控制在 10 分钟内。先静态检查结构和引用，再运行最能覆盖新增机制与保留修复的定向测试，随后在真实渲染界面检查主要新入口与触控布局。检测到失败即记录原因并修正，再针对受影响点复核，持续累计实际用时。动态验收达到预算时记录剩余范围并暂停后续运行，追加动态检查按该次明确确认执行。构建、签名和发布工件核验单独记录。

| 验收面 | 必要证据 |
| --- | --- |
| 角色与套装 | 动作顺序、来源持续伤害、加成只应用一次、首次触发、刷新、零命与满命 |
| 剧情叙事 | 对照原前两章的用词、词长、句长与人物口吻；逐场核对来由、动机、具体关心、战后回应和转场因果 |
| 祝福与奖励 | 6 条池结构、并集去重、候选权重、普通与精英奖励、首通及试用一次领取 |
| 存档与抽卡 | 旧局总幕数与既有内容、选中祝福、保底和大保底连续性 |
| 三模式新内容 | 明确候选与预算入口及具体旧怪基准；旧主题隔离，当前伤害链、主动攻击率、六行动输出及峰值、玩家 DOT 防护与跨技能群攻衔接 |
| 搜打撤 | 固定三幕、全部主题无放回选三、每主题三图、最终幕首领、独立容器、新物品与原经济 |
| 手机界面 | 固定页内关键按钮可达，长内容不挤出操作区；窄屏安全区、滚动与返回、目标选择、立绘和图标 |
| 动画与音频 | 跳过、加速、切后台、场景切换、重入与中断后的状态一致性 |
| 保留功能 | 当前实装的背包保护、重排、队伍行动段、祝福与修理补给修复 |

界面检查应实际打开角色详情、抽卡或试用、章节关卡、首领战、搜打撤新地图、容器和背包。查看动画中返回、连续点按、目标消失和音频场景切换时的处理。若环境只支持静态检查，则结果明确记为静态检查，真实渲染与设备项目继续保留待验证状态。

新增入口或状态文案后，固定页应约束内容高度、必要时让内容区滚动，保持底部操作按钮在可用视口内；特别检查试用完成后的抽卡入口和带长说明的确认页。战斗画面应显示当前节点已选背景，重入与旧档回退不重新抽图；把场景、配置和随机状态一起核对。

剧情验收在整合前完成全文连续通读，并对照原两章样本与改写案例复核，不能仅检查对白标识、段数和界面是否能够显示。确认读者不依赖设计说明也能理解路线、行动动机和场景衔接，并能指出人物在关心什么、怎样回应彼此，而不是笼统评为“温暖生动”。读到省略式单字指令、连续战术口令和格言串联时，结合实际动作语境判断缺失的信息和互动，再改成符合人物口吻的自然表达，不按单字匹配机械替换；功能界面简洁与剧情叙事舒展分别验收。整合后的真实界面只需重点检查修改段落的换行、滚动、继续按钮和演出衔接，仍计入既定的受影响功能验收预算。叙事通读结论与程序检查结果分别记录，程序通过不等于文案已通过。

仅修改常量的数值版本，在该次任务明确要求跳过游戏测试时按要求执行，并在记录中写明跳过范围。发布工件的版本、签名与可安装结构仍按实际构建结果核验。验收记录直接保存实际命令、范围、耗时、日志与结论；计划和未执行项目使用对应状态。

## 第八阶段 发布与后续核验

发布里程碑依次为设计定案、数据与资源齐备、功能整合完成、定向验收通过、构建与签名核验、获得本次适用的发布确认、上传与下载核对。每个里程碑记录版本或提交标识、责任范围、完成时间和证据位置。更新说明使用玩家语言交代新增内容与修复；工程细节保存在本流程和设计档案。

构建时核对版本名与递增版本码、包标识、签名证书摘要、正式更新源、资源完整性和安装包校验摘要。发布后读取正式发布页和更新清单，确认下载资产、版本和校验摘要与批准工件一致。最后把设计、资源清单、验收记录、更新说明和构建结果关联到同一版本，完成归档。

## 每次新角色可复用的归档结构

角色定案使用统一章节：角色与玩法、属性与技能、伤害和时序、遗物、祝福、剧情与获取、搜打撤、美术与音频、数值依据、实现与验收状态。每份档案保留一张标识表、一张参数表、一张资产表、一张验证表和一段玩家文案；剧情归档另保留原两章语言样本、人物口吻说明、场景因果提纲与全文通读结论，作为下一次新增角色的固定模板。版本补充记录只写本次变化，历史完成证据继续保留，最新事实以对应版本的实际验证文件为准。
