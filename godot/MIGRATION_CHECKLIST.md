# gachaWeb → Godot migration coverage report

Audit date: 2026-10-16. Source: sibling `gachaWeb`, baseline documented in its `VALIDATION.md` as `efc603092cca72a78939b3f09781fadc2df85e73`, with the local empty-slot export correction. This report separates working JavaScript functionality from unused data and proposed features, records the corresponding native evidence, and identifies remaining acceptance checks. The native implementation has passing model, battle, integration, storage and UI-controller suites plus selected desktop interaction checks; this is not a claim of exhaustive platform or visual QA.

## Verification legend and scope

`SOURCE` means reachable source UI or executable mechanics. `DATA` identifies descriptions or extension points without working source gameplay. `QUIRK` identifies executable source behavior that differs from its description. `MODEL`, `BATTLE`, `INTEGRATION`, `STORAGE`, and `UI` refer to the corresponding `tests/test_*.gd` scripts and `validation/*.log` files. `DESKTOP` means the named interaction was observed in an actual native window. `READ` means implementation inspection only. `PASS` applies to the explicitly named assertions, not every possible case in the acceptance column. `partial` and `PENDING` identify untested cases; they do not necessarily indicate missing implementation. UI-controller tests run headlessly and are distinct from desktop visual observation.

Latest recorded results: **184 model + 552 battle + 124 integration + 16 storage + 128 UI checks = 1,004 passing checks, zero reported failures.** Current import, test-suite and scene-smoke logs contain no `SCRIPT ERROR` or `ERROR:` entries. Static catalog comparison matches all 20 JSON-serializable top-level keys. Desktop observations cover the home page, story pre/post dialogue, manual attack, automatic victory/relic reward, summon reveal/summary, and persistence after restart. The 480 × 800 portrait test checks native layout bounds headlessly; portrait screenshots, phone touch and Android/iOS installation have not been verified.

The source contains 10 playable character definitions, 30 player skills, 9 enemy definitions, 23 enemy skills, 2 chapters with 10 stages, 20 dialogue scripts containing 133 lines, 2 active summon pools, 5 relic slots, 9 possible relic substats, 5 simulated recharge bundles, 2 gold-shop items, and 20 Abyss echo rewards. Every original stage currently has one wave. The original browser UI has Home, Stages, Summon, Team, Codex, Shop, Growth, and Abyss pages; save management is inside Home, and relic management is inside Growth. A native layout may reorganize these screens while retaining their functions.

Only Kaldi and Ayla have supplied portrait artwork. `流火荒原.png` is the supplied landscape. Other original characters use element symbols. Native procedural artwork, manual target selection, multiwave support, and any additional training system are enhancements and should be named as such.

## Source quirks requiring an explicit native decision

Limited-pool featured identity differs from the roll flag; the GA-06 formula describes actual source behavior. Banner “73 draws” language is off by one relative to the counter threshold. The original pool interface accepts arbitrary counts, so native public API input validation is appropriate hardening rather than a gameplay omission.

Status timing runs at full-round end. First actor after a queue refresh bypasses the freeze/stun check present in ordinary advancement. Electrify sets a flag and appears visually, but `canAct` ignores it; no chain-damage behavior exists despite the comment. Poison is a working registered status but none of the supplied 30 player/23 enemy skills applies it. Direct-hit invincibility does not protect from burn/poison ticks. Shield absorption retains the source minimum 10% raw damage leak. Healing and status effects resolve their targets independently, so a lowest-HP target can change between a heal and the following status.

Abyss stat application omits `spdMult`, although 超频矩阵 describes +8% speed. The same application clamps carried HP to at least 1 when any stat reward exists, accidentally reviving a fallen hero. Rogue combat hooks read saved selectedRewards without checking current battle type, allowing their damage/energy/healing effects to influence story battles. Native run-scoping, speed application and preserved zero HP are tested corrections documented in `validation/BATTLE_COVERAGE.md`.

Abyss defeat clears the build and party state while preserving currentFloor; the source defeat text suggests a restart but the model requires an explicit reset to return to floor 1. Source entry does not gate pending reward choices, so leaving/re-entering can bypass a node. Character focus min/max normalization can produce totals below 1 when only one or two eligible heroes exist; weighted selection still normalizes its own candidate weights. The native pending-choice gate is tested; dedicated focus-normalization edge assertions remain open.

Story entry charges stamina before checking party emptiness. Relic equip can detach a previous wearer before rejecting an unowned destination. The native model validates these cases before mutation, with atomic-rejection tests. Source saved-file parsing is permissive for syntactically valid wrong-shape JSON and source storage-write failures only log errors; native strict validation/atomic persistence improves this behavior. Native save paths should be separate from the previous prototype and original browser data.

## Native differences from the working source

The native game preserves the original catalog and gameplay loop while deliberately extending or correcting several behaviors. These differences should be considered when comparing saved games or combat outcomes.
